## 1. 先确定研究边界与论文问题

已完整阅读你提供的引言。它的逻辑链是：轮腿平台的移动优势 → 任务级理解需求 → 几何地图缺乏属性语义 → 外观相似物体可能具有不同任务属性 → VLM/LLM 与传统执行器分层协作。这个逻辑能够用于开题，但论文还缺少明确假设、相关工作对比、可验证贡献与实验协议。

本路线落实为民用巡检、救援辅助环境中的自然语言导航与观察任务，例如“到指定设备附近停下并拍照”“在不阻塞通道的位置等待”“不确定设备标识时先补拍再决定”。不展开作战掩护选择、防护能力优化或载荷对准威胁的实现。

建议第一篇论文暂定题目：《面向轮腿机器人巡检的证据约束语义任务规划与执行验证》。这是工作题目，最终题目由实际结果决定。

第一篇的最小问题：当物体外观相似、语义属性不确定时，相比直接让大模型生成导航目标，显式保存属性证据、允许拒绝判断或补充观察、在执行前检查可达性，是否能提高任务正确率，并减少不合理指令？

建议假设：证据约束与执行校验有帮助，但会增加观察次数和延迟。论文需要同时量化收益与成本。大模型组合、提示词修改、换成 Go2-W 平台本身都不自动构成创新。先复现基线，再决定方法差异。

第一阶段不同时承担低层运动控制创新、SLAM 创新、开放世界语义创新和多机协同。优先复用厂商运动能力与成熟导航，把贡献集中在任务属性表示、不确定性处理和执行验证。若始终只做平地导航，应明确 Go2-W 是验证平台，不能宣称提出轮腿运动算法；若主张轮腿特有收益，后续必须增加对应平台能力对照实验。

## 2. 对这版引言的具体修改建议

1. “足式通过能力”“效率更好”等属于需引用的经验结论，应给定地形、模式和比较条件，避免写成任何环境下都成立。
2. “自主能力主要集中于底层”“传统方法无法理解语义”过于绝对。已有语义地图、语言导航与机器人任务规划工作，应写清它们在你的具体任务上缺什么。
3. 不要把 VLM、开放词汇检测、分割、材质识别当成一个现成模块。它们可能需要不同模型与传感器，输出可靠性不同。
4. 纸箱与水泥块示例揭示了“外观推测不等于物理事实”，但材质名称也不能证明防护性能。厚度、内部结构和实验条件等未被确认时，应保留未知，不能由模型常识生成物理保证。
5. 用民用的“相似设备、不同标识/任务属性”作为可重复实验更容易定义真值。属性由已知实验物体、登记信息或人工复核建立，不能以大模型输出作为真值。
6. 分层架构之后补充：现有工作比较 → 具体缺口 → 方法概述 → 三项可验证贡献。贡献先写成待验证目标，不写“显著提升”或虚构数值。
7. 引言里的“通信受限自主性”若保留，就必须实测离线/断网行为；否则缩小该主张。“实时性”也要报告端到端延迟与失败处理。

建议贡献草案：①带来源与时效的对象属性表示；②面向未知属性的补充观察/拒绝执行机制；③统一场景协议下的基线、消融与实机验证。这些仍需文献检索确认新颖性。

### 8.2 明确三个不同层次

1. 几何模型：能显示机器人外观。
2. 动力学资产：质量、惯量、碰撞、轮关节方向等正确，落地后稳定。
3. 运动控制能力：有适配 Go2-W 的控制器/策略，能够按速度目标移动与停下。

只有第 1 项不能宣称完成 Go2-W 仿真。普通 Go2 没有 Go2-W 的轮关节，不能直接替代；URDF 转成 USD 也不会自动产生可靠运动策略。

资产核对表：来源及许可、版本/提交号、关节名与顺序、单位、基座坐标、惯量、碰撞形状、轮半径与轴向、驱动模式、关节限位、地面摩擦、相机与雷达安装外参。写入 `sim/assets/README.md`，供应商资产保持原样，自定义转换脚本另存。

首选复用已有 Isaac 做相机/场景与高层导航实验。若没有可用 Go2-W 运动控制，先用简化移动底盘跑通高层闭环，标明“功能代理”，此结果不算 Go2-W 动力学或实机验证；同时单独解决 Go2-W 控制适配。

官方 unitree_mujoco 的配置列出了 go2w，但文档明确目前主要提供低层控制验证 [4]。它可作为控制接口/模型核查的可选支线，不能当作已经实现了高层速度服务或自主导航。第一篇论文不必同时维护 Isaac、MuJoCo、Gazebo 三套主实验。

### 8.3 导航闭环的验收顺序

场景保持简单：地面、墙、几个固定设备。先使用仿真真值定位调通导航；然后才加入实际估计的里程计/定位。论文必须分别报告真值定位与真实传感器输入结果。

依次验收：机器人稳定 → 低速移动与停止 → 相机/深度/雷达数据 → TF 与时间戳 → RViz 地图显示 → 静态目标导航 → 障碍附近停靠 → 任务取消。采用 Nav2 等成熟导航栈时，需要准备正确的机器人轮廓、传感器输入、里程计和控制接口，它不是装好就能运行的完整 Go2-W 系统。

坐标至少明确 `map → odom → base_link → sensor`；仿真节点使用仿真时间并验证 `/clock`。保存目标、轨迹、碰撞事件、失败原因与随机种子。第一轮用少量不同起点检查闭环，不要马上启动大规模训练。

## 9. 阶段 D：从人工语义到模型语义

采用由易到难的四步，每一步都能独立检查失败来源：

1. 人工对象与属性 + 规则选择 + 导航：确认任务定义、目标定位和执行可行。
2. 人工对象与属性 + LLM 结构化任务：只评估语言解析和计划，不混入视觉错误。
3. 视觉识别 + 人工复核属性 + 规划执行：评估检测、定位和对象关联。
4. 视觉属性候选 + 证据约束 + 不确定性处理 + 执行校验：形成待验证方法。

开始只选一个能输出结构化结果的视觉模型与一个规划模型。记录版本、许可、输入分辨率、推理参数、显存占用与时延；是否本地推理由真实测试决定。24 GiB 显存不能保证大型 VLM、LLM 和渲染同时运行；可以串行推理、降低图像分辨率、缓存结果，或独立进程按需加载。使用在线接口时单列网络延迟与离线失败，别把服务中断算成模型推理正确。

对象记录建议字段：`object_id`、`label`、`pose`、`frame_id`、`timestamp`、`attributes`、`source`、`evidence_refs`、`status`。属性状态采用 confirmed/inferred/unknown；`inferred` 不升级为真实物理能力。模型自报 0.9 不是经过校准的概率，需用独立验证集评估。

任务记录包括 `task_id`、`instruction`、`target_object_id`、`action`、`preconditions`、`timeout_s`。只允许白名单动作：`inspect`、`navigate_to`、`wait`、`stop`、`request_observation`。这些是民用观察任务接口设计，不是任意代码执行。

规划器只输出结构化计划；执行器核查：格式、动作许可、对象是否存在、证据是否过期、目标是否可达、任务是否已取消。不通过就拒绝、重新观察或请求人工确认。感知到的文字属于观测数据，不能覆盖执行器规则。禁止直接执行模型生成的 Python/shell，也不让模型输出电机命令。

先用纯 Python 离线回放做这套逻辑，再封装成 ROS 节点；这样更容易定位错误，不必每次启动仿真。

## 10. 阶段 E：设计一篇能被审稿人检查的实验

### 10.1 数据与任务

先做 10–20 个开发场景验证协议，再冻结一份独立测试集。按场景/对象实例划分，避免同一物体换个视角就同时进入开发与测试。覆盖：清晰标识、外观相似但标签不同、遮挡、弱光、缺失属性、无法到达、目标不存在、图像或通信超时。

每个样本记录：场景、对象真值、任务文本、起点、传感器设置、可接受目标集合、任务成功条件与失败类别。真值由人工核查/实验登记建立，不用被评估模型自评。仿真真值不能直接泄漏给被测试方法。

可先按 3 个场景 × 每场景 10 个任务 × 3 次重复规划规模：每方法 90 次。真实机器人可按 2 个环境 × 5 个任务 × 3 次重复规划：每方法 30 次。这只是预算示例，不保证统计效力；先用开发实验估计方差，再确定最终样本量。不要为了出现显著结果不断追加测试或换指标。

### 10.2 公平基线与消融

| 组别 | 目的 |
|---|---|
| 规则 + 同一对象输入 + 同一导航器 | 判断是否真的需要大模型 |
| 直接 VLM/LLM 规划 + 同一导航器 | 基础大模型方案 |
| 完整方法 | 证据、不确定性、执行校验全部启用 |
| 去掉证据约束 | 测量证据表示作用 |
| 去掉补充观察/拒绝机制 | 测量未知处理作用 |
| 去掉任务级执行校验 | 离线/仿真评估错误计划影响，实机保留基本保护 |
| 人工真值语义输入 | 分析感知误差与规划误差的分界 |

若复现相关工作，只能称“某工作启发的基线”或明确列出复现改动，不能把自己简化的模型当成原论文完整结果。固定模型、提示词、token 预算、导航参数、起点与任务分布；补充观察有成本，要报告时间与观察次数，别让完整方法无限重试。

### 10.3 指标与统计

- 任务成功率：由预先定义的终态与观察结果判断，不以模型自称完成为准。
- 条件规划正确率：给定同一对象输入时，计划满足任务要求的比例。
- 不合理计划率、拒绝率、可回答任务覆盖率；拒绝所有任务不能算高性能。
- 已执行任务中的错误率与覆盖率同时报告，评估置信阈值带来的权衡。
- 端到端完成时间、规划/感知耗时的中位数与 P95、额外观察次数。
- 导航成功、定位误差、碰撞/急停事件、人工介入次数；单独统计平台执行问题。
- 资源成本：GPU 显存、平均推理耗时；若用在线模型，记录调用量与实际费用。

比较方法使用相同任务配对。二元成功率可报告 Wilson 置信区间；考虑同场景多次运行的相关性，优先按场景/任务分组自助采样，不把视频帧当独立样本。连续指标报告分布而不只均值。失败要标为感知、对象关联、语言解析、计划、导航、通信或超时，不删除失败运行。

实机的属性标签只验证任务语义，不代表验证材料强度或物理防护能力。模拟场景结果也不自动代表户外复杂地形能力。

## 11. 阶段 F：实机前你必须取得的信息

向设备负责人/厂家确认并填入 `docs/hardware_inventory.md`：

- 准确型号、版本/配置、固件、是否开放二次开发权限。
- 可用的高层运动服务；其命令、状态、停止和模式切换说明是否针对 Go2-W。
- 相机、深度、雷达、IMU 数据是否可导出；频率、时间戳、标定与话题/SDK 接口。
- 机载计算单元、系统、可安装软件范围，网络接法与开发网卡。
- 允许的负载、供电方式、实验场地、实体急停/遥控接管流程。

没有这些信息，不能承诺某条 Go2 示例命令对你的 Go2-W 有效。支持同种底层 IDL 不等于支持相同高层服务。

实机里程碑：①设备断开运动指令，只读状态与传感器；②录包，在本机离线回放；③核对坐标、时间和标定；④操作者在场，验证停止/接管；⑤受限场地低速短距离指令；⑥已知目标导航；⑦简单民用观察任务；⑧与仿真一致的对照协议。

每次记录固件、SDK、软件提交、场地、操作者、网络状态和电量。先使用厂家原生高层运动能力，不把低层力矩控制作为第一篇语义导航论文的必经路径。故障恢复与超时停止放在确定性执行层，不依赖模型及时回复。

当前电脑做开发和离线处理足够合适，但是否能随机器人移动要另行设计：第一轮可以在受控局域网中由本机推理，论文明确“外部计算”；后续再评估机载部署。不能把远程推理实验写成全机载自主。

## 14. 论文怎样逐步写出来

从现在建一个相关工作表，每篇记录：问题、平台、输入、语义表示、规划方式、真实机器人验证、指标、局限、与你的关系。先读 SayCan 与 VLMaps 的原始论文/项目页 [7][8]，再沿引用查语义地图、语言导航、可供性与不确定性方法。这两项是入门起点，不能代表完整或最新综述。正式开题/投稿前补查近两年文献，逐篇核对来源。

建议每周精读 1 篇、浏览 2–3 篇，先积累约 15–25 篇真正相关的论文。不要只堆引用数量。当前没有访问你的 Zotero，也没有生成未经核验的 BibTeX；有文献库后再用 Zotero skill 检索导出。

写作顺序建议：任务与假设 → 实验协议 → 系统和方法 → 结果与失败分析 → 相关工作与引言 → 摘要。引言随实际贡献修改，不让实验去迎合最早的故事。

论文结构：

1. 引言：具体需求、现有缺口、问题和贡献。
2. 相关工作：语义导航、语言机器人规划、证据与未知处理；比较适用条件。
3. 问题定义：可观测输入、允许动作、未知属性、任务成功和预算。
4. 方法：数据表示、结构化规划、执行校验、观察反馈；给流程图或伪代码。
5. 实验：仿真/实机平台、版本、数据划分、公平基线、消融、指标和统计。
6. 结果：主表、误差/成本权衡、失败案例；区分语义贡献与导航成功。
7. 局限与结论：属性真值、遮挡、计算位置、平台与场景泛化边界。

至少准备：系统架构图、任务与属性示例图、主结果表、消融表、延迟/覆盖率权衡图、真实失败案例。所有主表能从固定数据与脚本重新生成，禁止手填一个看起来更好的数值。

与导师先确认目标语言、毕业/课题要求、可接受 venue 和时间窗口，再按目标模板整理。没有实验结果之前不保证达到某个期刊等级；投稿费用、开放获取规则和日期在确定目标时查官网。

## 17. 相机选型、旋转激光雷达联动与对照实验（2026-10-26 增补）

### 17.1 结论与当前项目起点

在“确定使用旋转激光雷达、论文聚焦民用巡检语义规划”的前提下，建议：**硬件优先选择能输出同步左右原始图像、标定信息和可靠时间戳的双目设备；软件先完成单路图像 + 雷达，再增加双目深度 + 雷达。**预算或装配条件受限时，单目 + 雷达也能构成完整论文系统，不应为了双目推迟全部研究。

双目的价值主要是增加近中距离的几何观测与对象定位证据；不自动提升语言推理，也不能证明物体材质或承载/防护能力。旋转雷达也不替代视觉的标签、颜色、文字与类别理解。两者结合的目标是把“看见什么”和“在哪里、能否接近”关联起来。

是否值得购买双目，取决于工作距离、雷达垂直采样/近距离盲区、目标大小、照明与计算预算。当前未确定具体雷达型号，因此不能给出真实有效距离、毫米级精度或最终安装位置的承诺；先用下面的仿真扫描和设备参数完成决策，不先锁定品牌。

**项目状态修订说明：**第 3、8、15 节描述的是 2026-10-25 初次规划时的起点。2026-10-26 查阅现有文档及代码，项目已新增 Go2-W 相机、ROS 2 与运动训练链路，见 [Go2W键盘与相机](Go2W键盘与相机.md)、[Go2W_ROS2训练验收](Go2W_ROS2训练验收.md)。`scripts/go2w_ros2.py` 已发布 `/go2w/front_camera/image_raw` 与 `/go2w/front_camera/camera_info`。现有相机文档记录 640×480 RGB、相对机身约 5° 俯角，属于继续扩展的基础。本次只检查文档/代码，没有重新执行其验收；双目、旋转雷达与融合仍是本节提出的后续工作。

### 17.2 单目与双目到底有什么区别

这里的单目指一条 RGB 图像流；双目指两台经过标定并同步采样的相机，通过匹配获得视差。双目设备不一定是“两路彩色相机”：有的用双红外成像做深度，再配一台独立 RGB。购买前确认原始数据是否开放、RGB 与深度是否对齐、能否关闭主动投射器，以及实际采用哪一种深度原理。ToF、被动双目、主动双目不应混为一类。

| 比较项 | 单目 RGB | 双目视觉 |
|---|---|---|
| 物体类别、颜色、文字 | 常可满足语义模型输入，取决于成像质量 | 不因多一个镜头自动更准；可仍只用左图做语义 |
| 单帧距离 | 普通 RGB 没有直接公制深度；可借助雷达、已知几何、运动或学习深度 | 有标定基线时，可由左右匹配恢复公制深度 |
| 与雷达搭配 | 雷达提供距离，图像提供语义，结构清晰 | 可同时获得雷达稀疏测距与双目较稠密深度 |
| 近处/细小物体 | 雷达未采到时，二维目标难可靠定位 | 合适视场/最小距离内，可补充可匹配区域的几何 |
| 无纹理白墙/重复图案 | 语义仍可能可用；单目深度也可能推断错误 | 匹配容易缺失或混淆，不保证形成有效深度 |
| 弱光、模糊、反光/透明 | 识别与单目深度均可能退化 | 匹配也易退化；主动补光仍受距离/阳光/表面影响 |
| 远处目标 | 依赖雷达点密度及关联 | 视差变小，深度误差增加；不是全距离优于雷达 |
| 标定维护 | 内参 + 相机到雷达/机身外参 | 再增加左右外参、校正、同步与机械稳定要求 |
| 算力、带宽、记录成本 | 相对较低，但学习深度模型也可能很重 | 增加第二图像与匹配；若板载计算深度，主机负担可降低 |
| 论文实验价值 | 适合必要基线与简洁系统 | 适合研究“额外几何何时有用、成本多少” |

普通单目几何存在尺度歧义，但“单目永远不能得到公制尺度”也不准确：雷达、IMU/充分运动约束、已知尺寸或公制学习模型可以增加尺度信息；这些条件和误差必须显式报告。学习单目深度应是另一个实验组，不把它偷偷加进 RGB 基线。

对校正后的理想双目，`Z = fx × B / d`，其中 Z 为光轴方向深度（m）、fx 为像素焦距、B 为基线（m）、d 为视差（px）；推导见 [10]。一阶误差近似 `σZ ≈ Z² × σd / (fx × B)`。举例：fx=600 px、B=0.10 m、视差误差 0.5 px 时，2 m 约对应 3.3 cm 深度误差，5 m 约 20.8 cm。这只是理想传播计算，不是任何产品的精度承诺，未包含标定/同步/遮挡误差。

基线更大有利于远距分辨，但也增加左右遮挡差异、近距匹配难度和安装宽度；分辨率提高也会增加算力与带宽。不能只看“多少万像素”，要一起评估视场、焦距、基线与实际距离。

**对于当前论文：**若单目 + 雷达已能稳定定位目标，双目可能只带来小幅收益，甚至因为延迟降低闭环成功率。这个负结果也有价值，前提是实验公平、误差分析清楚，不能预设双目一定更好。

### 17.3 能不能两种都用、怎样公平比较

可以。最优先的做法是让同一双目设备产生两种输入条件：A 只使用左图 + 雷达，B 使用左图语义 + 左右图计算深度 + 雷达。这样视角、曝光、左图成像和安装位置尽量一致，一次采集即可离线配对比较。

这叫“单路输入与双目输入的对照”，不等于比较“一台专用单目产品与一台双目产品”的硬件性价比。若是双红外 + 独立 RGB 设备，保持两组使用同一 RGB 语义流，并如实称为 RGB+雷达 与 RGB+双目深度+雷达，不声称把左彩色图作为唯一变量。

额外再装一台单目相机有两种实际用途：①高分辨率/大动态范围 RGB 用于文字与语义，双目用于几何；②不同方向扩大覆盖范围。但这会增加外参、时间同步、供电、USB 和视角遮挡问题。第一篇优先一套设备，后续有明确盲区再增装。软件禁用右图不等于真正省下了硬件功耗，成本分析需分别说明。

推荐主对照：

| 组别 | 允许输入 | 用途 |
|---|---|---|
| A | 统一 RGB + 雷达 + 固定定位源 | 最小完整基线 |
| B | 同一 RGB + 真实左右匹配深度 + 雷达 + 同一定位源 | 测量双目增量收益 |
| C | 同一 RGB + 双目深度 + 同一定位源，不用雷达做对象深度 | 可选：区分不同深度来源；固定定位源可能仍由雷达提供，必须写清 |
| D | 同一 RGB + 单目学习深度 + 雷达 + 同一定位源 | 可选：比较低额外硬件方案，额外记录模型训练来源 |
| O | 同一 RGB + 仿真真值深度 + 同一定位源 | 只作误差上界分析，不是双目主结果 |

所有主要组别都保留基础导航保护，C 的“禁用雷达深度”不应混淆成物理移除雷达。如果另做完全无雷达定位导航，那是另一项系统实验，定位误差也会变化，应单独成表。

核心设计：固定语义模型、左图/公共 RGB、提示词、导航、定位、场景和任务；只改变对象定位所使用的几何输入。先用同一录制数据评估深度/对象位置；再让 A/B 分别闭环运行，因为不同决策会改变后续观测，一份录包不能证明两组闭环任务成功率。

以 2×2 设计控制论文规模：传感器输入 A/B × 规划方法（直接规划/证据约束）。这能检验改进究竟来自更好的深度还是任务规划。每格 30 个固定任务 × 3 个种子只是预算示例，不是统计效力保证；使用开发集估计方差后冻结规模，实机可先缩小可重复子集。

### 17.4 旋转激光雷达怎样与相机联动

先确认是 2D 单线旋转雷达还是 3D 多线旋转雷达，以及垂直视场、扫描线分布、最小距离、每点时间戳和 IMU。2D 扫描只覆盖一个高度平面，可能完全扫不到图像里的设备；不能据此给整张图像配上可靠深度。3D 雷达也可能因垂直视场和点间距漏掉近处、矮小或细窄目标。

第一层联动：**语义与几何关联（首选实现）。**图像检测/分割得到对象区域；把经过时间补偿的雷达点变换到相机系后投影；利用对象区域内的有效点估计对象表面和三维位置；再送入对象地图与任务规划。

静态同一时刻的投影形式是 `pC = TC_L × pL`、`u ~ K × pC`。这里只适用于相机前方且模型一致的点：必须过滤 Z≤0、越界点，并考虑畸变/校正后的内参。移动场景还要把各雷达点从采样时刻变换到相机曝光时刻，不能仅乘一次静态外参。

“框内所有雷达点取平均”很容易把背景墙、前景栏杆与目标混在一起。优先用分割区域、深度簇、可见性/z-buffer、时序跟踪与有效点数约束。取中位数只能抑制部分离群点，不保证得到真实目标。对象状态保存 depth_source、有效点数、位置协方差/质量分数、观测时间与是否冲突。

第二层联动：**雷达与双目互补（A/B 后实现）。**雷达采样足够且关联可靠时给对象距离；雷达点稀疏或缺失时使用通过置信度与左右一致性检查的双目深度。两者冲突就保留冲突、检查遮挡/时间/标定或重新观察；不是无条件平均。二者共享姿态与标定误差，不能假定独立后用错误的加权平均制造虚假的高置信。

第三层联动：**定位/建图融合（可选支线）。**先用雷达 + IMU 提供稳定定位，相机负责语义。后续才考虑视觉-雷达-惯性紧耦合：它改变状态估计器、时间同步要求和维护成本，不是把三种 ROS 话题放一起。FAST-LIVO2 是可参考的原作者实现，但当前原仓库的依赖路线是 ROS 1/catkin，不能称为本机 ROS 2 Jazzy 即装即用 [13]。研究主线不是 SLAM 时，优先不改定位器。

第四层联动：**任务反馈。**规划器发现对象定位不可靠时请求补充观察，在受控巡检任务中停止后重新取图/点云，或由导航器移动到可达的观察位置。重观测目标是确认设备/标签/位置，不把额外传感器当作材质真实性的证明。

旋转扫描在一个周期内依次采点，不是一张瞬时照片。以 10 Hz 为例，一圈历时约 100 ms；机身平移 0.5 m/s，期间约移动 5 cm，还可能旋转。因此要保留每点相对时间，使用 IMU/里程计去畸变；未知时间字段时先做静止融合，再清楚报告动态局限。相机 30 Hz、雷达 10 Hz、IMU 200 Hz 只是可用的初始仿真设置，实际取决于硬件。

软件 ApproximateTime 只按时间戳配对，不会给相机硬件同步，不修正时钟漂移，也不会去除一圈点云的运动畸变。硬件触发/PTP 是否可用需看具体传感器；曝光开始/中间时刻、雷达一圈起止时间戳的定义都要核对。ROS message_filters 还需要兼容 QoS 与合理队列，见 [14]。

### 17.5 在当前电脑上怎样逐步搭仿真

以下是后续实施计划，**本次未修改控制代码或宣称传感器已实现**。继续使用已有 Isaac Sim 环境与 Go2-W 资产，先在单机器人、平地、小场景中验收，不把多相机渲染塞进大规模并行强化学习。

**步骤 1：保留现有基线。**

先按 `docs/Go2W_ROS2训练验收.md` 的现有方式启动，保存前置 RGB、CameraInfo、TF、时钟及控制模式。不要为了加传感器重写原有运动模块。把当前控制器、相机内参、机器人资产与测试脚本版本记入运行元数据；仅参考原验收记录不代表今天又通过了验证。

**步骤 2：构造左右相机 rig。**

基于当前前置相机建立一个固连机身的 stereo_rig，左右 optical frame 的内参一致，双目在同一仿真时刻曝光。选择当前前置相机为左相机时保持其视点不变，右相机按基线平移；若采用 rig 中心为原点，应确保 A/B 都使用新的同一左视点，不把视点改变当成深度收益。

先以 640×480、基线 0.10 m、约 80° 水平视场作为软件测试例子；之后扫描 0.06/0.10/0.16 m 基线、不同分辨率与目标距离。这些不是最终设备规格。不要复制旧内参到新分辨率：裁剪、缩放与焦距都要重新核算 CameraInfo。先固定曝光、关闭自动曝光差异，确保左右图不是来自相邻两帧。

检查左/右相机横向顺序、视差正负号、基线单位、相机轴约定；ROS optical 通常 x 右、y 下、z 前，要与 Isaac/USD 坐标变换核对。不要靠“RViz 看着差不多”认定外参正确。

**步骤 3：用真正的匹配算法产生双目深度。**

先离线保存同步左右图、内参/外参，再执行校正、StereoSGBM 等可解释基线、无效视差过滤和深度计算；稳定后再考虑学习匹配。检查 OpenCV 具体接口的视差缩放，例如常见定点输出需要除以 16，不能直接当像素值。保存原始视差、有效掩码和运行时间，不只保存漂亮伪彩色图。

模拟器 `distance_to_image_plane` 等几何深度只放到评估分支，与估计深度分开命名。由光线追踪直接获得深度不包含真实双目匹配的全部失效机制，不能直接称为“双目测量”。如果使用 Isaac 提供的专门深度相机模型，要核查它具体模拟了什么、是否仍从真值生成，再如实标注。当前与 latest 文档 API 可能有差异，不直接粘贴新 API 覆盖现有入口 [11]。

**步骤 4：加入与目标设备相近的旋转扫描。**

在机身添加 lidar_link，配置水平/垂直扫描、线数、扫描频率、距离范围和盲区；先用一堵墙和已知尺寸物体核对点云距离及坐标。区分完整一圈与每帧部分扫描，验证每圈点数/时间跨度。Isaac RTX 雷达涉及渲染与扫描累计，配置不匹配可能只输出部分扫描，应按所装版本核对 [12]。

需要时输出 PointCloud2，保留 intensity、ring、逐点 time 等实际算法需要的字段；模拟器/桥接是否提供这些字段要检查，不能凭空补一个相同时间戳冒充真实逐点时间。只有真正 2D 扫描或经过明确高度过滤的投影才用于 LaserScan，不能无说明地把全部 3D 点当作二维安全地图。

若暂时只有理想整帧点云，可先做静态对象定位，但不能用它宣称验证了旋转雷达去畸变。动态传感器建模不足时，把限制写入实验。

**步骤 5：先静态完成相机—雷达投影。**

机器人不动，在 1/2/3/5 m 等预设位置放置棋盘平面、箱体、细杆与有文字的设备模型。验证投影边缘、内参、外参方向与遮挡关系；保存“RGB + 投影点 + 双目有效区 + 真值误差”的四联图。真值距离应与估计量一致：表面光轴深度、欧氏距离、对象中心三者不等价，不混着比较。

**步骤 6：接入对象地图和统一深度接口。**

让上层规划器只接收统一对象记录，不知道自己使用的是雷达还是双目；深度来源、质量与时效仍保留在记录中。提供 `lidar_only`、`stereo_only`、`hybrid` 的几何估计配置；所有组用同一公共 RGB 做识别。先人工对象掩码隔离几何误差，再启用真实视觉分割区分感知误差。

**步骤 7：从静止扩展到运动。**

先停车观察，再低速直行，最后转弯和轮腿模式下的小幅姿态变化。比较瞬时点云假设与时间补偿，不把人为放大的时间窗口当作完成同步。运动实验同时记录平移/角速度、曝光时间、采集/接收时间与丢帧；退化可能来自机身振动，也可能来自驱动时间戳或队列积压。

**步骤 8：控制退化因素，固定测试集。**

先每次只改变一个因素：低纹理、重复图案、低照、局部遮挡、反射表面、细物体；再进行少量组合测试。噪声分两层：图像层模糊/曝光差异，以及深度/雷达层缺失/离群点。简单给真值深度加高斯噪声不能替代真实左右匹配失效。

时间偏移可扫描 0/10/30/50 ms、外参旋转扰动 0/0.5/1°、平移扰动 0/1/3 cm，作为明确标注的敏感性测试，不是正常校准精度承诺。用真值外参产生观测后，仅扰动算法使用的估计外参，模拟“校准误差”；不要移动整个传感器又同步更新算法外参，那是在改变安装位置。

**步骤 9：ROS 发布与录制。**

建议新增下列话题；都是规划名称，不表示当前已存在：

```text
/go2w/stereo/left/image_raw       sensor_msgs/Image
/go2w/stereo/right/image_raw      sensor_msgs/Image
/go2w/stereo/left/camera_info     sensor_msgs/CameraInfo
/go2w/stereo/right/camera_info    sensor_msgs/CameraInfo
/go2w/stereo/depth_estimated     sensor_msgs/Image
/go2w/lidar/points               sensor_msgs/PointCloud2
/go2w/imu/data                   sensor_msgs/Imu（须说明真值/模拟噪声）
/go2w/objects                    后续统一对象接口
/clock /tf /tf_static            时间与坐标
```

`depth_estimated` 要说明是光轴 Z 还是射线距离、单位 m 还是 mm、编码 32FC1 还是 16UC1、无效值怎么表示。`CameraInfo` 内外参、P 矩阵、左右基线符号需遵循相应 ROS 接口。左右图与参数时间一致，不用推理结束时间覆盖采集时间。可把仿真真值放 `/evaluation/ground_truth/*`，主算法订阅列表显式排除。

先用 `ros2 topic list/info/hz` 检查接口与 QoS，短录包确认 image/CameraInfo/points/TF/clock 均可回放，再延长记录。回放时只允许一个仿真时间源，避免录包 `/clock` 与活跃模拟器同时发时钟。

**步骤 10：离线测几何，再测闭环与实机。**

离线固定轨迹、相同图像/雷达数据，报告几何/关联精度；闭环固定初始条件与任务，报告完成率/延迟/观察次数。最后在真实设备上重新做内参、双目、相机—雷达和机身外参检验，仿真外参不能直接当真实标定。

### 17.6 最常见的问题与排查顺序

| 现象 | 可能原因 | 首选排查 |
|---|---|---|
| 深度整体差 10/100/1000 倍 | 基线单位、视差缩放、mm/m 混用 | 已知距离平面，打印 fx/B/d/Z 与单位 |
| 左右图匹配全黑/深度负值 | 左右顺序、校正、视差范围错误 | 检查极线、共同视场与正视差 |
| 图像有目标但雷达没点 | 线间距、盲区、遮挡、材质/距离、2D 扫描高度 | 看原始点云和传感器参数，不强行补可信值 |
| 投影静止也错 | 外参方向、optical 轴、内参/畸变不一致 | 静态平面与多深度目标，核查变换定义 |
| 静止正确，转弯错 | 时间偏移、滚动快门、整圈点云畸变 | 逐点时间 + 姿态补偿，检查曝光时刻 |
| 彩色点云看着不错，对象位置却错 | 框内背景混入、跨传感器遮挡 | 分割、深度聚类、可见性检查 |
| 深度有洞后导航误判 | 缺失值被置零/当成自由空间 | 保留有效掩码，未知状态不冒充可通行 |
| 几帧后才出现第一张图 | 渲染预热/异步读回 | 以数据就绪和时间戳检查，不复用空或旧缓冲 |
| 左右图尺寸一致但实际不同步 | 分别在不同仿真 tick 渲染 | 共享采集时刻，检查帧编号与实际输出 |
| 雷达点数不稳/只有扇区 | 完整圈累计与渲染频率不匹配 | 核查 scan/tick 配置和累计输出 |
| ROS 有话题却收不到图 | QoS 不兼容、域/网卡或订阅配置 | 先单话题订阅再做同步，不先调大队列 |
| 启用 VLM 后“实时”失效 | GPU 渲染/模型争用、同步拷贝、排队 | 拆分计时，限制队列、异步处理/离线回放 |
| 重置后地图/TF 跳变 | 仿真时间回退、旧队列/状态未清空 | reset 清理同步队列、对象轨迹与滤波器 |
| 实机标定随走动变差 | 安装件变形、松动、线缆拉扯、震动 | 检查刚性与复验标定，隔振不能破坏相对固定关系 |

两路 640×480 RGB8、30 Hz 的原始图像仅像素数据就约 55.3 MB/s（约 199 GB/小时，十进制单位），还没算深度、点云和消息开销。当前磁盘预算不适合无计划长录：先录 30–60 秒样本估算实际压缩/吞吐；开发期间按需降帧和选段，正式对照保持同一编码。JPEG 等有损压缩可能改变纹理与视差，不能 A 组无损 B 组有损。

3D 旋转雷达的广视场不等于语义覆盖 360°：前置相机只能解释自己的视场，后方点云可以用于几何地图，不能凭空拥有物体类别。雷达强度也受距离、入射角和仪器影响，不直接当材质真值。

### 17.7 本论文应测哪些新增指标

几何层：对象表面/位置误差、有效深度覆盖率、有效雷达点数、对象关联正确率；按距离、目标大小、纹理和遮挡分别统计。只在有效像素上算误差会掩盖大量缺失，因此误差与覆盖率必须一起报告。

系统层：任务成功率、错误对象选择率、未知/拒绝率、补充观察次数、导航终态误差、人工介入次数；再报告感知/融合延迟 P50/P95、端到端完成时间、实际频率、丢帧、显存与数据体积。

论文主问题保持为“几何观测质量如何影响证据约束语义任务”，相机对比是验证方法对不同传感配置是否稳健的实验维度。若仅得出“双目比单目好”，通常不足以支撑方法贡献。更有解释力的问题是：雷达稀疏到什么程度双目才有收益？低纹理时如何识别深度不可信？不确定性传播能否避免错误任务执行？额外延迟是否抵消几何改进？

相机与雷达都不能通过外观/深度自动验证隐藏物理性质。相似设备的真实身份、维护状态或任务属性仍需标识、登记资料或人工核验；论文应将这类证据和纯视觉推断分开。

建议顺序：第 1 个小周期完成左右同步图像与静态匹配；第 2 个完成旋转点云与静态投影；第 3 个完成 A/B 离线对象定位；第 4 个接入已有 ROS/导航闭环并测试运动同步。每周期约 3–7 个实际工作日只是估算，有控制/驱动/API 问题时按验收推进，不为了赶日期跳过误差核查。

购买前由你补齐：雷达准确型号与数据字段、是否使用自带还是外加 IMU、目标距离区间、环境光与室内外比例、最小目标大小、安装宽度/刚性、USB/以太网接口、计算位置和预算。然后用仿真确定基线/视场需求，再借测或购买，避免先买设备后发现无法获取同步原始图。
